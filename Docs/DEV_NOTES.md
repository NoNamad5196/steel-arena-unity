# Protocol Arena 개발 기록

## 2026-09-04 / 1차 MVP 기반 구현

문제: 새 Universal 2D 템플릿에는 카메라 외에 게임 오브젝트와 UI가 없어서, 수동 Inspector 연결은 누락된 Reference를 만들 가능성이 있었다.

원인: 프로젝트가 생성 직후 상태였고 재사용할 프리팹이나 씬 구성이 없었다.

해결: `RuntimeInitializeOnLoadMethod`로 시작점을 하나 두고, Play 시 uGUI와 전투 표시를 코드에서 생성했다. 씬은 하나만 유지하며 Rule Setup, Battle, Result 패널의 활성 상태를 전환한다.

선택 이유: MVP 단계에서 사용자의 반복적인 Editor 설정을 없애면서도, 전투 모델과 UI 책임은 별도 클래스로 유지할 수 있기 때문이다.

## 2026-09-04 / Rule 평가 구조

문제: Condition 만족 여부와 Action 실행 가능 여부를 동시에 우선순위 판단에 사용하면, 화면에 표시된 "첫 번째로 일치한 Rule" 규칙과 실제 선택이 달라질 수 있었다.

원인: 공격 쿨다운이나 사거리 같은 실행 제약을 Rule 검색 단계에 섞을 가능성이 있었다.

해결: `RuleEvaluator`는 Condition만 검사하고 첫 번째 일치 Rule을 반환한다. 쿨다운과 사거리의 실행 결과는 `CombatSimulation`이 처리하며 Decision Log에 성공 또는 실패 이유를 함께 남긴다.

선택 이유: 위에서 아래로 검사해 첫 Condition이 참이면 선택한다는 게임 규칙을 코드와 로그가 그대로 설명하도록 하기 위해서다.

## 2026-09-04 / 검증 경계

문제: 런타임 UI와 결합된 상태만 확인하면 Rule 순서, HP 임계값, 재시작 초기화의 회귀를 빠르게 찾기 어렵다.

원인: 버튼을 직접 눌러 보는 검증은 결과는 보여 주지만 핵심 로직이 실패한 위치를 좁히지 못한다.

해결: Rule 첫 일치, 순서 변경, HP 30% 경계, 전투 종료, 재시작 초기화를 EditMode 테스트로 분리했다.

선택 이유: Unity Play 확인과 순수 로직 테스트가 서로 다른 종류의 오류를 보완하도록 하기 위해서다.

## 2026-09-04 / 첫 Unity 컴파일

문제: 첫 배치 검증에서 C# 컴파일은 성공했지만 테스트 결과 XML이 생성되지 않았다. Unity 6.6은 `FindFirstObjectByType` 사용도 폐기 예정 경고로 보고했다.

원인: 테스트 폴더에 Test Assembly Definition이 없어 Test Runner의 검색 대상이 되지 않았고, 초기 구현에서 인스턴스 순서가 필요 없는 검색에 구형 API를 사용했다.

해결: 런타임 및 Editor 테스트용 Assembly Definition을 추가하고 `FindAnyObjectByType`로 변경했다. Test Runner 배치 실행에서는 `-quit`을 제거해 Runner가 결과 저장 후 직접 종료하게 했다.

선택 이유: 테스트를 Unity Test Runner가 명시적으로 발견하게 하고, 불필요한 컴파일 경고를 남기지 않기 위해서다.

## 2026-09-04 / Play Mode Dropdown 표시 오류

문제: 첫 Play Mode 테스트에서 Rule 1의 Condition이 `HP <= 30%`가 아니라 `Option B`로 표시됐다.

원인: `DefaultControls.CreateDropdown`이 예제 옵션 세 개를 가진 Dropdown을 생성하는데, 게임 옵션을 기존 목록 뒤에 추가했다. enum 인덱스와 화면 옵션 인덱스가 서로 달라졌다.

해결: Condition과 Action 옵션을 추가하기 전에 `ClearOptions`를 호출했다. Play Mode 테스트에서 초기 표시와 우선순위 이동 뒤 표시를 모두 확인한다.

선택 이유: 표시 텍스트만 고치는 대신 Dropdown 데이터와 Rule enum의 0 기반 인덱스를 일치시켜 선택 콜백까지 함께 바로잡기 위해서다.

## 2026-09-04 / Play Mode 시간 기반 테스트

문제: 수정 후 테스트가 600프레임 안에 전투가 끝나지 않았다고 실패했지만, 같은 Rule의 순수 시뮬레이션은 정상 종료했다.

원인: 배치 모드는 600프레임을 약 0.23초에 처리해 실제 `deltaTime` 누적이 충분하지 않았다. 프레임 수를 전투 시간으로 간주한 테스트 가정이 틀렸다.

해결: `realtimeSinceStartup` 기준 3초의 안전 제한을 두고 `timeScale`을 높여 게임 시간을 진행하도록 변경했다.

선택 이유: 실행 환경의 프레임 처리 속도와 무관하게 전투 종료를 검증하기 위해서다.

## 2026-09-04 / Rule 편집 발견성 개선

문제: Rule Setup에서 조건과 행동을 변경할 수 있다는 점과 현재 선택 영역이 눈에 잘 띄지 않았다.

원인: Unity 기본 Dropdown 형태를 거의 그대로 사용해 화살표가 보이지 않았고, 우선순위·조건·행동의 시각적 구분도 약했다.

해결: 각 행을 `번호 | IF | Condition ▼ | THEN | Action ▼ | Priority` 구조로 재배치했다. Condition은 주황색, Action은 청록색 테두리와 명시적 화살표를 사용하고 호버·선택 색도 추가했다.

선택 이유: 별도 튜토리얼 없이도 클릭 가능한 영역과 Condition→Action 관계를 즉시 이해하게 만들기 위해서다.

## 2026-09-04 / 핵심 루프 전면 피벗

문제: Rule을 직접 편집한 뒤 바로 전투하는 구조는 기술 시연은 가능했지만, 보상을 획득하고 빌드가 강해지는 오토배틀러의 기대감이 없었다.

원인: Rule 편집 자체를 핵심 플레이로 가정해 준비 단계의 수행, 보상 선택, 성장 결과라는 감정 곡선을 만들지 않았다.

해결: 기존 Rule UI와 관련 전투 모델을 제거하고 `Preparation → Calibration → 3택1 Reward → Auto Battle → Run Report` 흐름으로 교체했다. 미니게임 점수는 보상 수치에 직접 반영한다.

선택 이유: 플레이어의 짧은 조작이 보상 선택으로 이어지고, 선택한 빌드가 자동전투에서 회수되는 구조를 만들기 위해서다.

## 2026-09-04 / 피벗 후 테스트 컴파일

문제: 새 미니게임 테스트에서 사용한 `Is.AnyOf`가 프로젝트에 포함된 NUnit 버전에서 제공되지 않아 첫 컴파일이 실패했다.

원인: 최신 NUnit 문법을 현재 Unity Test Framework의 NUnit API에서도 사용할 수 있다고 가정했다.

해결: 동일한 검증을 호환되는 `CollectionAssert.Contains`로 교체했다.

선택 이유: 패키지를 추가하거나 올리지 않고 현재 Unity 6.6 프로젝트의 테스트 환경을 유지하기 위해서다.

## 2026-09-04 — 쉬운 한국어 UI와 1차 타격감 개선

- 프로젝트 표시명을 `강철 투기장`으로 정리하고 화면 문구를 쉬운 한국어로 통일했다.
- 강화 6종을 `튼튼한 장갑`, `강화 무기`, `고속 장전기`, `가속 장치`, `비상 수리`, `연속 공격`으로 변경했다.
- 운영체제의 한글 폰트를 우선 불러오고, 찾지 못했을 때 Unity 기본 폰트를 사용하는 대체 경로를 추가했다.
- 동력 맞추기에 3초 카운트다운, 완벽 구간, 시도별 점수, 결과 색상 피드백을 추가했다.
- 보상 카드에 강화 종류와 현재 수치에서 선택 후 수치로 바뀌는 내용을 표시했다.
- 자동 전투에 공격 돌진, 피격 흔들림, 회복 확대, 피해/회복 숫자를 추가했다.
- 배치 모드에서 스크립트 재컴파일은 성공했지만 로컬 Unity 라이선스 클라이언트 재연결이 반복되어 테스트 러너 완료는 보류했다.

## 2026-09-06 — 제출용 2차 버전

- 보상 풀을 9종으로 확장하고 `고속 탄막`, `중장 반격`, `가속 돌진포` 조합을 추가했다.
- 조합 한쪽을 보유하면 다음 보상에서 짝 강화를 하나 보장해, 3라운드 안에도 의도적인 빌드 선택이 가능하게 했다.
- 전투를 `고철 돌격병 → 파쇄 대장` 2연전으로 바꿔 빌드가 서로 다른 적을 상대하도록 했다.
- 전투 배경 이미지를 생성해 프로젝트 리소스로 포함하고, 제작 프롬프트를 함께 기록했다.
- 외부 음원 라이선스 문제를 피하기 위해 짧은 UI·전투 효과음을 런타임 파형 합성으로 제작했다.
- 강화 표시 규칙을 `UpgradePresentation`, 적 데이터를 `EnemyCatalog`, 음향을 `ProceduralAudio`로 분리했다.
- 순수 C# 전투 로직을 별도 컴파일하고 밸런스 시뮬레이션을 실행했다. 기본 기체는 보스에게 패배했고, 기존 공격/수리 빌드와 새 고속 탄막 빌드는 보스에게 승리했다.
